# Smart Sync architecture audit — 13 October 2026

Baseline: the user's complete, SHA-256 verified v2.10.11 ZIP. Original extraction is preserved separately.

| Domain | Current authority / relationships | Integration |
|---|---|---|
| Inventory | Product IDs; batches determine units; packs are a representation. `setStock`, `applyEffect`, `rebuildStockFromOpening`, Stock forms, bulk imports and Market apply modify stock. | Persist exact committed relative unit/batch movements; keep a shared supervised checkpoint; derive a bounded current projection. Preserve deficits explicitly. |
| Transactions | `tx` draft plus saved-day snapshots overlap. `normalizeTxIds` historically repairs missing IDs. Edits replace records; deletions remove active records. | Canonical transaction identity across saved/current records. Permanent before/after amendment and tombstone events. Similar-looking different IDs require review during enrollment. UUIDs for new records; device sequences order events independently of clocks. |
| Market | Version-8 Market blob contains lists, requests, suppliers, item history, grouped purchases and embedded payments. Compatibility arrays repeat the same rows. Purchases/payments link to transaction IDs. | Flatten canonical arrays, purchase headers, items and payments; exclude compatibility aliases and device selection. Reconstruct the existing blob after merging; validate linked purchase/payment records. |
| Finance | AES-GCM vault with locally wrapped key, PIN and recovery key. Bank movements derive from deduplicated saved/current transactions plus private events. | Keep credential wrappers local. Require existing Financial PIN for sync sessions. Encrypt exchanged payloads with a separate shared passphrase; locally retain private event revisions encrypted with the existing vault key. Checkpoint account boundaries use IDs, not timestamp authority. |
| Reports | `calc`, `recordCalc`, `anaAggregate`, product history derive from source transactions, saved openings and stock snapshots. | Preserve transaction snapshots; canonical union once per day. Preserve original reconciliation archives and record decisions. Current accounts derive from checkpoint plus differences from accounted transactions. |
| Persistence | IndexedDB schema 7, atomic business saves, collection delta writes, revision guard, Web Locks/journal fallback. | Schema 8 adds isolated synchronization state/identity and indexed immutable events. A synchronous commit observer appends events in the same durable transaction as business changes. Failed atomic writes restore both. |
| Backup | Unified Full Backup v28, SHA-256, validation, safety copy and checked restore; includes encrypted unfinished forms. | Add synchronization state and events; never transfer installation identity. Sync and restore file formats remain distinct. Re-read exported recovery files before enrolling. |
| Temporary audit | Seven-day display/audit cleanup. | Never expire sync events, tombstones, applied IDs or checkpoints when temporary adjustment rows expire. |

Native mutation entry points include retail submit/edit/delete/held groups, POS submit/edit, cash-move sheet, Stock add/edit/bulk/import/adjust/archive/restore, Market purchase/reversal/supplier payments/list/request changes, Notes CRUD, pricing Settings and Financial movement/review/PIN/recovery workflows. The storage commit observer covers both atomic and ordinary native persistence, instead of relying on a partial list of button handlers.

No legacy quantity or financial balance is inferred from historical depth. Initial pairing uses explicit identity confirmation, both read-back-verified recovery backups, transaction/product/field conflict review, and supervised stock/account verification. Snapshot event boundaries protect business activity continuing after the captured snapshots. Both devices must accept and acknowledge the same checkpoint; a single import remains pending.

Offline file encryption supplies confidentiality and shared-secret authentication (not per-person nonrepudiation). A checksum only detects corruption. The Android Studio project and a physical APK/device are not supplied: browser/PWA file APIs can be tested; actual Android picker/download/share integration must be reported separately and supported with bridge fallbacks.
